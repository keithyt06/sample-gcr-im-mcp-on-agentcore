# Security model

This page describes the trust boundaries, the token model, what data is stored where, the IAM layout, and the known limitations. It is written for the operator who deploys the sample and for reviewers. This sample is **not production-ready**; review it against your own requirements before you use it with real data.

## Components and trust boundaries

```
 MCP client (Kiro, Claude Code, Codex, Cursor, Amazon Quick)
      |  HTTPS, Authorization: Bearer <MCP access token>
      v
 [B1] API Gateway HTTP API  (+ optional custom domain; optional CloudFront + WAF on AWS Global)
      |                     route throttling: 50 rps / burst 100 (default stage),
      |                     POST /register 5/10, GET /authorize 2/5
      +--> oauth Lambda       OAuth 2.1 authorization server (well-known, DCR, authorize,
      |                       callback, token, WeCom QR status)
      +--> middleware Lambda  verifies the MCP token, loads the user's IM credential,
               |              signs with SigV4
               v
 [B2] AgentCore Runtime  InvokeAgentRuntime (IAM / SigV4 only)
               |   one microVM per user session (session id = HMAC(userId))
               v
      container (MCP server on :8000/mcp) --> vendor CLI (lark-cli | dws | wecom-cli)
                                                 |
 [B3]                                            v  HTTPS as the user
                                             IM open platform (Feishu / Lark / DingTalk / WeCom)
```

| Boundary | What crosses it | Control |
|---|---|---|
| B1 Internet → API Gateway | Any HTTP request | TLS. The MCP token is verified in the middleware Lambda. OAuth endpoints are public by design (RFC 8414 / 9728 / 7591). API Gateway route throttling. On AWS Global you can add `ingress.edge: cloudfront` + `ingress.waf: true` (AWS managed rule groups + a rate rule of 1000 requests per 5 minutes per IP). AWS China has no CloudFront/WAF option in this sample; throttling is the only edge control there |
| B2 Lambda → AgentCore Runtime | JSON-RPC body + custom headers (`X-Amzn-Bedrock-AgentCore-Runtime-Custom-User-Id`, `-User-Token`, `-Authorize-Url`, `-Request-Id`, `-Caller`) | The Runtime is only reachable with SigV4 `InvokeAgentRuntime`, which only the middleware and oauth Lambda roles are allowed to call. The container therefore **trusts these headers**. Client headers are never forwarded; only the raw JSON-RPC body is. The `Mcp-Session-Id` is derived server-side; the client's value is ignored. Methods starting with `im/` are rejected by the middleware, and the container also requires `Caller: control` for them |
| B3 Container → IM | User token (DingTalk: `--token` argv; Feishu/Lark: env; WeCom: per-user encrypted config) | Each call runs the CLI with `execFile` (no shell), a per-call temporary working directory, and an environment of only `PATH`, `HOME`, `LANG`, `NO_COLOR` plus adapter variables (no `AWS_*`). Flag names come only from the catalog; values are separate argv entries |

## Token model

| Token | Format | Lifetime | Where it lives |
|---|---|---|---|
| MCP access token | HMAC-SHA256 signed `{userId, exp}` (key derived from the root key) | **1 hour** | Client only. Verified statelessly (no database lookup per request) |
| MCP refresh token | Random, stored as SHA-256 hash | 90 days, rotated on every use; replay revokes the whole family | DynamoDB `refresh#<hash>` |
| Authorization code | Random, stored hashed, single use, bound to client_id + redirect_uri + PKCE challenge | 120 s | DynamoDB `code#<hash>` |
| DCR `client_id` | HMAC-signed list of redirect URIs (stateless, nothing stored) | No expiry | Client only |
| Incremental-authorization token (in `authorize_url`) | HMAC signed with a separate key; cannot be used as an access token | 10 min | Tool results |
| Root key | 64 random characters, generated by CloudFormation | Until the stack is deleted | Secrets Manager `<slug>/root-key`. Lambdas cache it for 5 minutes |

PKCE (S256 only) is mandatory. Clients are public (PKCE only) by default; a client registered with `client_secret_post` / `client_secret_basic` (for forms that require a secret, via `npm run register-client`) gets a stateless secret derived from the root key, and any presented secret must match. Redirect URIs must be loopback (`127.0.0.1`, `localhost`, `[::1]`, any port), the Amazon Quick hosts (AWS Global only), or an HTTPS host in `oauth.extraRedirectHosts`. Custom URI schemes, fragments and userinfo are rejected. The allowlist is checked at registration **and** at `/authorize`.

### Revocation timing

`npm run users -- revoke <userId>`:
- Takes effect **immediately** for new logins and refresh-token grants: no new MCP access token is issued.
- An **already-issued MCP access token stays valid until it expires, at most 1 hour.** This is by design: access tokens are short-lived and verified without a per-request database check.
- The middleware caches a user's IM credential for up to **60 seconds**.
- The user's IM credential secret is force-deleted at once, so IM calls fail as soon as the cache expires.
- Revocation is permanent. There is no `unrevoke`. For Feishu/Lark/DingTalk the IM identity stays bound to the disabled user, so the person stays blocked. For WeCom a revoked identity that scans again is refused.

To cut off everyone at once (for example, after a suspected root-key leak), rotate the root key (`aws secretsmanager put-secret-value` on `<slug>/root-key` with a new random value). Every access token, refresh token and DCR client id becomes invalid within the 5-minute Lambda cache, and all users must reconnect.

## Data stored

| Data | Store | Encryption | Retention |
|---|---|---|---|
| IM app secret (Feishu/Lark/DingTalk) | Secrets Manager `<slug>/im-app` | AWS managed key | Deleted with the stack |
| HMAC root key | Secrets Manager `<slug>/root-key` | AWS managed key | Deleted with the stack |
| Per-user IM credential (user access + refresh token; WeCom encrypted CLI config) | Secrets Manager `<slug>/users/<userId>` | **Dedicated KMS CMK** (rotation on) | Created at runtime, **not** deleted by `destroy`; use `npm run teardown:extras` |
| OAuth state, codes, refresh-token hashes, user records (`im`, IM user id, timestamps, `disabled`, `approval`) | DynamoDB table (on-demand, PITR) | AWS managed key | Short-lived items have a TTL; table deleted with the stack |
| Logs | CloudWatch Logs (Lambda, API access log: 30 days; Runtime log group created by the service) | Default | Lambdas log a hash of the user id, never tokens, codes or secrets |

The KMS CMK has `RemovalPolicy.RETAIN` so that a mistaken stack deletion does not make user secrets unreadable. Schedule its deletion with `npm run teardown:extras` after `destroy`.

## IAM summary

| Role | Main permissions |
|---|---|
| Runtime execution role | ECR pull of the image asset; CloudWatch Logs under `/aws/bedrock-agentcore/runtimes/*`; Feishu/Lark only: read `<slug>/im-app`; WeCom only: get/put/create (with this stack's CMK) and tag (only the `WecomUserId` tag key) secrets under `<slug>/users/*`, plus encrypt/decrypt with the CMK. **No `bedrock:InvokeModel`.** Trust policy: `bedrock-agentcore.amazonaws.com` with `aws:SourceAccount` and `aws:SourceArn` conditions |
| oauth Lambda | Read root key and IM app secret; user secrets under `<slug>/users/*`; CMK; the DynamoDB table; the base-URL SSM parameter; WeCom only: `InvokeAgentRuntime` on this runtime |
| middleware Lambda | Read root key and (redirect IMs) user secrets + CMK decrypt; `InvokeAgentRuntime` on this runtime; the base-URL SSM parameter |
| refresh Lambda (Feishu/Lark/DingTalk) | `secretsmanager:ListSecrets` on `*`; get/put/describe/delete under `<slug>/users/*`; read IM app secret; CMK |
| alarm Lambda (optional) | `ssm:GetParameter` on the configured webhook parameter |

`Resource: "*"` appears only for `ecr:GetAuthorizationToken` and `secretsmanager:ListSecrets`, which have no resource-level permissions (see the [Service Authorization Reference](https://docs.aws.amazon.com/service-authorization/latest/reference/)). The refresh Lambda filters by name prefix in code.

## Threats and mitigations

| Threat | Mitigation / status |
|---|---|
| **WeCom QR phishing and any-tenant access.** The WeCom QR flow has no tenant boundary: anyone with a WeCom account in any organization can complete it. Anyone you send a QR link to authorizes **as themselves** for **your** MCP client and AWS bill. Conversely, an attacker can send a victim a QR page from their own deployment | Set `wecom.requireApproval: true` (new users wait for `npm run users -- approve`). Pending users never receive a token. Tell users to scan only QR codes they started themselves from their own MCP client |
| Anonymous clients starting many WeCom QR sessions (each holds a microVM up to 300 s) | `GET /authorize` route throttle (2 rps / burst 5), `wecom.maxPendingQr` global cap (default 20) and a per-IP cap of 3 |
| Prompt injection in IM content asks the agent to run destructive tools | Destructive tools (`delete`, `remove`, `recall`, `revoke`, `transfer_owner`, …) require `_confirm: true`. **The LLM sets this flag itself**, so it is a speed bump that relies on the client and the user reviewing tool calls, not a security control. Use a client that asks before tool calls |
| Prompt injection asks the CLI to spawn processes | Commands with process or daemon flags (`--agent-cmd`, `--daemon`, `--yolo`, …) and DingTalk `dingtalk-tag connect*` / `manage login` are marked unavailable in the catalog. WeCom `extra_identity_context` text is stripped from results |
| Cross-user access inside the Runtime | One microVM per user session. User IDs are never used in file paths. Per-call temp directories are deleted after the call |
| **WeCom runtime role can read every WeCom user's secret** (known limitation) | One execution role serves every microVM, and AgentCore passes no per-session identity to IAM, so access cannot be scoped to one user's secret. A code-execution bug in one user's `wecom-cli` call could read other WeCom users' credentials. Mitigated by the narrowed role above and the process-flag denylist. Feishu/Lark/DingTalk runtimes have no access to user secrets (the token arrives per request) |
| Token leakage in errors or logs | The CLI runner never includes the command line in error text (DingTalk passes the token in argv). Lambdas log `hashUserId` only |
| Supply chain of the vendor CLIs | CLI versions are pinned in `shared/versions.ts`. Each tarball's sha512 is checked against `container/build/cli-integrity.json` before unpacking, with no `npm install` of transitive dependencies. The base image is pinned by digest. In China the packages come from npmmirror, a third-party mirror; the integrity check covers that |
| DingTalk refresh errors wiping users | Only explicit grant-revoked errors delete a user's credential; app-credential errors, 429, 5xx and unknown codes are treated as transient |
| China public endpoint | Without ICP filing the default URL returns 403 from the internet. Use an ICP-filed custom domain |
